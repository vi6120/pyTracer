A green test does not mean your fix worked.

Agents are nondeterministic. Re-run a failed one and the model and tool responses come back different every time, so when a test turns green you cannot tell whether your code change fixed it or the model just drifted.

Capture a run once, replay it anywhere.

The same failure reproduces the same way every time, with no live model calls and no API spend.

CaptureRecord the run, down to each model call and tool result, with the branch and commit stamped on it.
FreezePin the recorded model and tool responses as mocks, along with the clock, timestamps, UUIDs and RNG.
ReplayRe-run on any branch in full, partial or live mode, or freeze everything except the one step you changed.
ClassifyGet a fixed, still-failing or diverged verdict per scenario, or no verdict with the reason why.

The support agent that sent the wrong items.

A customer asks a support agent to exchange an order. The agent confirms, but the exchange goes out with the old item IDs as the new ones: a one-line bug in the glue code between the model and the tools. Re-running it live proves nothing, because the model words things differently each time.

  1. Captured. The failing conversation is recorded with its branch and commit, every model call and tool result.
  2. Turned into a test. pytracer record makes it a scenario asserting the right items are exchanged, so CI goes red.
  3. The fix PR. Comment /pytracer try and it replays the exact conversation: fixed.
  4. A PR that only looked like a fix. A rename, bug still there: still failing, not a lucky green run.
  5. The PR it cannot judge. It changes the exchange call itself: cannot judge, naming that call and what to do, instead of guessing.

Replay that survives real nondeterminism.

Choose how much to hold frozen: full freezes the recorded model and tools, partial keeps the tools frozen and runs the model live, and live re-runs everything. Or freeze everything except the one step you changed. Every mode asserts the route the agents took, not just the final output, and replay stays faithful on real agents: streamed responses and concurrent or repeated tool calls replay in order, the clock, timestamps and UUIDs are pinned, the RNG is seeded, and live side effects are surfaced.

A verdict is only drawn from a run that stayed on its recording. If a branch makes a call the recording cannot serve, you get cannot judge with that call named, never a lucky fixed. If the baseline itself drifts, it is cannot reproduce. A branch that fails exactly as before is still failing, whatever else changed.

The open problems in agent replay.

That record-and-replay works for agents is understood. The hard, still-open parts are what come next, and they are where pyTracer lives.

A verdict, not pass/fail

pyTracer answers fixed, still failing or diverged across branches, and says cannot judge with the reason rather than call a branch fixed on a run that left its recording.

Replay that survives nondeterminism

One unmarked clock, timestamp, UUID or RNG read silently runs live and breaks a deterministic replay. pyTracer pins all of them, so a run reproduces beyond the mocks.

Matching a re-worded call

Matching by name and call count misses reordered or re-worded inputs. pyTracer matches on hashed inputs with a fuzzy and positional fallback, and marks a non-exact match instead of serving the wrong recording.

Multi-agent routes and side effects

Assert the route the agents took, freeze just the step under test, and surface any live call during replay, so a green replay never hides a real side effect.

Questions, answered.

The docs go deeper. Open an issue on GitHub, or email services@pytracer.com.

How is pyTracer different from tracing or eval tools?
Tracing shows you that a run happened; eval scores an output. pyTracer freezes a captured run and re-runs it deterministically on another branch, so you learn whether your code change is what fixed the failure, not just that today's run passed. See the full comparison.
What does deterministic replay actually mean?
The recorded model and tool responses are injected back in during replay, so the agent follows the exact same path with no live API calls. The same failure reproduces identically every time.
What do "cannot judge" and "cannot reproduce" mean?
They are pyTracer refusing to guess. Cannot judge: the branch made a call the recording cannot serve, so its result is not a frozen one; pyTracer names that call and tells you what to do. Cannot reproduce: the baseline itself drifted, usually because the run's settings were missing (pass them with --env-file).
Do I have to change my agent code?
With a framework adapter (LangGraph, CrewAI, AutoGen, OpenAI Agents), no: register the adapter and its model and tool calls are captured and replayable as they are. Otherwise, add the @op decorator to the functions that call models and tools. One or two lines each, and it does not change their behavior.
How fast is it, and what does it cost to run?
A replay makes no model calls, so it costs nothing in API spend. The gateway sustained 3,600 spans per second for 30 minutes on a laptop with no lost spans, and the whole stack runs on a free-tier VM. The benchmarks page has every number with its hardware and command.
Is it open source? Can I self-host?
Yes to both. The client toolchain is Apache-2.0 and the hosted server components are AGPL-3.0; all 12 packages are on PyPI and the repository is public. Self-host the gateway and stores as a Docker stack, or point the SDK at the hosted gateway.
Does my prompt data leave my machine?
Only the spans you capture are sent to the gateway you configure, which can be your own. You control what is instrumented and where it goes, and sensitive values are redacted locally before they leave.
