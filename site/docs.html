What pyTracer is

pyTracer is an agent test and replay platform. It captures what an AI agent does (its LLM calls, tool calls, reasoning steps, and handoffs), replays a past run deterministically by injecting the recorded responses instead of calling live services, and regression-tests agents in CI. Its headline capability is cross-branch reproduction: take a captured failing run and re-run it against a different branch with the model version and recorded tool responses held frozen, so you learn whether a branch actually fixed the bug.

Requirements

  • Python 3.10 or newer (3.12 recommended).
  • Nothing else to just instrument and replay locally.
  • For capturing to a gateway and browsing traces: a running pyTracer gateway with its stores (ClickHouse, PostgreSQL, Redis), self-hosted or the hosted service.

Installation

Install the whole platform, or just the SDK in your agent:

# the whole platform
pip install pytracer-all

# or just the client SDK
pip install pytracer-sdk

# the CLI, with the extras you need
pip install pytracer-cli[stores]   # browse/record traces
pip install pytracer-cli[runner]   # cross-branch reproduce

The packages are standard PyPI wheels, so uv works the same way, either adding to a project or into an environment:

uv add pytracer-sdk                # add to your project
uv pip install pytracer-all        # or into the active environment

pyTracer is a Python library; there is no npm package. A TypeScript SDK (and a vitest integration for JS/TS agents) is on the roadmap, not yet released.

Quickstart (no services)

You can run the whole loop locally with no gateway or database, using an in-memory transport. This instruments an agent, captures its run, and replays it.

import pytracer_sdk as pytracer
from pytracer_sdk import SpanKind

sink = pytracer.InMemoryTransport()
pytracer.configure(sink, service_name="researcher", branch="main", commit="quickstart")

@pytracer.op(kind=SpanKind.TOOL, tool_name="search")
def search(q): return [f"doc about {q} #1", f"doc about {q} #2"]

@pytracer.op(kind=SpanKind.AGENT, agent_name="researcher")
def run(task): return "Summary: " + "; ".join(search(task))

print(run("climate change"))
pytracer.flush()
print(f"captured {len(sink.spans)} spans")

A complete, runnable version lives in the repository under examples/quickstart.

1. Instrument your agent

Add @op to the functions that call models and tools. This is one or two lines per function and does not change their behavior.

import pytracer_sdk as pytracer
from pytracer_sdk import SpanKind

@pytracer.op(kind=SpanKind.TOOL, tool_name="search")
def search(query: str) -> dict:
    ...  # your real tool

@pytracer.op(kind=SpanKind.LLM)
def call_model(prompt: str) -> str:
    ...  # your real model call

@pytracer.op(kind=SpanKind.AGENT, agent_name="researcher")
def run(task: str) -> str:
    return call_model(str(search(task)))

Capture is fire-and-forget: it never blocks your agent, and if the gateway is unreachable your agent keeps running.

2. Ship spans to a gateway

Point the SDK at your gateway so spans flow into the trace store. Stamp each run with the branch and commit so a captured failure is tied to exact code. Use an https:// endpoint in production.

pytracer.configure(
    pytracer.HTTPTransport("https://gateway.pytracer.com", api_key="YOUR_PROJECT_KEY"),
    service_name="researcher",
    branch="main",
    commit="abc123",
)

Redaction runs before anything leaves your process. As each span closes, its input, output and error message are scanned and secrets are replaced in place with a labeled placeholder: provider API keys (OpenAI, GitHub, AWS, Slack), Luhn-valid card numbers, and email addresses, out of the box. Pass your own Redactor to extend the defaults:

from pytracer_sdk import Redactor, RedactionRule, DEFAULT_RULES

pytracer.configure(
    pytracer.HTTPTransport("https://gateway.pytracer.com", api_key="YOUR_PROJECT_KEY"),
    service_name="researcher",
    redactor=Redactor(rules=[*DEFAULT_RULES, RedactionRule("ssn", r"\b\d{3}-\d{2}-\d{4}\b")]),
)

Rejected spans are surfaced, never silently dropped. A gateway can return 202 and still reject individual spans (for example one missing branch/commit). The transport keeps a running rejected_spans count, logs a warning with the gateway's reason, and calls an optional on_rejection(count, errors) callback, so CI can fail instead of losing spans quietly. Capture stays fire-and-forget: a raising callback is logged, not propagated.

def alert(count, errors):
    raise SystemExit(f"gateway rejected {count} span(s): {errors[0]}")

transport = pytracer.HTTPTransport(
    "https://gateway.pytracer.com", api_key="YOUR_PROJECT_KEY", on_rejection=alert,
)
pytracer.configure(transport, service_name="researcher", branch="main", commit="abc123")
# ... run the agent ...
print(transport.rejected_spans)  # 0 when every span was accepted

3. Turn a failure into a test

When a run fails, browse recent captured runs and scaffold a test from one, with no hand-writing of files. These commands need the store client (pip install pytracer-cli[stores]).

pytracer traces list --failed           # find the failing run
pytracer traces show <trace_id>          # inspect its span tree
pytracer record <trace_id> --agent myapp.agents:run --entry task="summarize the doc"

record writes the trace's spans to JSONL and creates a collection: a small YAML file naming the agent to run, the recorded trace to mock from, and the assertions that should hold.

# tests/collection.yaml
name: captured-suite
scenarios:
  - name: summarize-happy-path
    agent: myapp.agents:run          # import path "module:callable"
    entry: { task: "summarize the doc" }
    trace: traces/summarize.jsonl    # the recorded spans
    mode: full                       # full | partial | live
    assertions:
      - { type: no_errors }
      - { type: contains, needle: "summary" }

4. Run a collection

Replays inject the recorded tool and model responses, so the run is deterministic and touches no live services.

pytracer run tests/collection.yaml

Replay modes: full (recorded model and tools), partial (recorded tools, live model), and live.

For higher fidelity, streaming model responses replay token by token, and concurrent or repeated tool calls replay their recorded responses in order. The engine can also freeze the clock and seed the RNG around a run (so a live or partial replay stays reproducible beyond the mocks), and it records the external tool calls a replay makes, so you can flag non-idempotent or conflicting writes.

How matching works. A replay looks up each recorded response by the op's identifier (its tool or op name) and an exact hash of its input, so by default a replayed input must match what was captured. Three scenario fields control what happens when it does not:

  • fuzzy: true - when an exact input misses, fall back to the nearest recording for that op by input similarity, so small drift (a timestamp in a prompt, a reordered field) still replays.
  • strict: true - fail the scenario on an unrecorded call instead of silently running it live. On by default in full mode.
  • sandbox: true - block outbound network during the replay, so a miss cannot fire a real side effect. On by default in full mode.

Replay injects at the @op seam. A run captured only through a framework adapter records spans but adds no interception point, so there is nothing to inject and the scenario runs live and fails loudly until you add @op to the functions that call your models and tools.

Scenario options reference

A scenario is data, so every behavior below is a field in the collection YAML:

scenarios:
  - name: refund-policy
    agent: myapp.agents:run
    entry: { task: "process the refund" }
    trace: traces/refund.jsonl
    mode: full                 # full | partial | live
    fuzzy: true                # fall back to the nearest recording on input drift
    strict: true               # fail on an unrecorded call (default: on in full)
    sandbox: true              # block the network during replay (default: on in full)
    live:   [send_email]       # run these ops live, freeze the rest of the run
    freeze: [charge_card]      # serve these from the recording, run the rest per mode
    writes: [charge_card]      # tools that mutate; a live call is logged as a write
    freeze_time: 1737331200    # pin time / datetime to this unix instant
    seed: 7                    # seed random and uuid4 for a reproducible run
    evaluate_changed_prompts: false  # run a frozen model op live if its input changed
    assertions:
      - { type: no_errors }
      - { type: contains, needle: "refunded" }
      - { type: route, expected: [planner, billing] }   # agents visited, in order
      - { type: tools_used, expected: [charge_card], exact: false }
      - { type: step_count, expected: 3, kind: tool }    # count spans of one kind

live and freeze are the selective, per-step freeze: freeze a whole recorded run except the one step under test, or vice versa. freeze_time / seed pin the clock, timestamps, UUIDs and RNG so a live or partial replay reproduces beyond the mocked responses. route, tools_used and step_count assert the path the agents took, not just the final output. evaluate_changed_prompts (also pytracer run --evaluate-changed-prompts) handles a fix that edits a prompt: when a frozen model op's input no longer matches the recording, it runs that op live so the edit is actually evaluated, rather than reporting a diverge a frozen replay cannot judge. It makes a live model call, so it drops the sandbox.

A few behaviors live on the commands rather than the file:

  • pytracer run ... --strict/--no-strict, --sandbox/--no-sandbox override those fields for a whole run; --json / --junit / --comment write machine, CI and PR-comment reports.
  • pytracer record --from-file trace.jsonl --agent ... scaffolds a collection from a locally captured trace, with no gateway or store.
  • pytracer reproduce --branch <ref> --baseline <ref> --env-file .env passes environment variables (API keys, endpoints) the agent needs into the isolated per-branch run, so a real fix is not reported still-failing for want of a key.
  • The gateway re-queues dead-lettered spans via POST /v1/dead-letters/requeue, so a storage blip does not lose accepted spans.
  • pytracer registry export collection.yaml bundle.json packs a collection and its recorded traces into one self-contained artifact; pytracer registry import bundle.json out/ materializes it back into a runnable directory, so a shared collection runs without the traces it points at going missing.

5. Gate branches in CI

Add the GitHub Action (see packages/cli/ci/github-action.yml). On every pull request it runs the collection and posts a pass/fail summary as a PR comment, failing the check if any scenario regresses. On a push it also auto-documents failures as deduplicated GitHub issues. A GitLab template is included too.

pytracer run tests/collection.yaml --json results.json
pytracer issues sync results.json --repo owner/name   # needs a GitHub token

Run collections in pytest

Installing pytracer-cli registers a pytest plugin, so agent regression tests run inside your existing pytest suite. Name a collection file to match *.pytracer.yaml and run pytest: each scenario becomes its own test, with -k filtering, reporting, and CI exit codes all working as usual.

pip install pytracer-cli[pytest]

# agents.pytracer.yaml is discovered automatically
pytest -v
# agents.pytracer.yaml::researcher-happy-path PASSED
# agents.pytracer.yaml::refund-policy        FAILED

Override the file pattern with the pytracer_glob ini option. A vitest integration for JS/TS agents is planned alongside the TypeScript SDK (not yet released - pyTracer is Python-only today).

6. Reproduce on any branch

When a teammate opens a fix, re-run the failing collection against their branch with the mocks frozen, so only the code changes. Needs the runner (pip install pytracer-cli[runner]).

pytracer reproduce --branch feature/fix-bug --baseline main \
  --collection tests/collection.yaml

It checks out each ref in its own isolated workspace, replays, and prints a per-scenario verdict of fixed, still failing, or diverged (a new, different failure), exiting non-zero unless every scenario is fixed. Each workspace installs the project under test and pyTracer itself, so your project does not need to depend on pytracer-cli. If the agent needs secrets or endpoints to run, pass them with --env-file .env so the replay reaches the bug instead of failing on configuration (and a real fix is not reported still-failing).

A runnable, self-contained example of exactly this is in examples/reproduce-demo: one command builds a buggy branch and a fix branch and reproduces the captured failure across them, with the mocks frozen.

Try on this branch, from a PR. Add the try-on-branch workflow and comment /pytracer try on any pull request: pyTracer reproduces the failure on that branch and posts the fixed / still-failing / diverged verdict back as a comment, updated in place on each push (pytracer reproduce --pr <number> under the hood).

Framework adapters

Instead of manual @op decorators, drop in an adapter for your framework and its LLM/tool/agent steps are captured automatically:

pip install pytracer-langgraph        # LangGraph / LangChain
pip install pytracer-openai-agents    # OpenAI Agents SDK
pip install pytracer-crewai           # CrewAI
pip install pytracer-autogen          # AutoGen

An adapter captures only what its framework reports. The LangGraph adapter sees calls made through LangChain, so a model call on a raw provider client, or a tool that is a plain Python function, is not captured; instrument those with @op. For the OpenAI Agents SDK, use the adapter's install() helper, which makes pyTracer the only trace processor; adding it with the SDK's add_trace_processor instead leaves OpenAI's own exporter in place, so runs would also upload to OpenAI when a key is set. Adapters capture only: replaying a captured run still needs @op, and an adapter-only run is flagged rather than replayed live.

Use cases

Regression-test a customer-support agent

Capture real conversations, turn the ones that went wrong into a collection, and run it on every pull request so a prompt or tool change can't silently reintroduce the same failure.

Prove a fix actually works

A user reports a bug. Capture the failing run, then use pytracer reproduce to re-run it against the fix branch with the model and tools frozen, so you know the code change is what fixed it, not luck.

Compare model or prompt versions deterministically

Freeze the tool responses and replay in partial mode against a new model or prompt, isolating the effect of that one change.

Share test suites across a team

The registry turns collections into versioned, forkable, access-controlled artifacts with pull requests and discovery, the way Postman collections worked for API testing.
