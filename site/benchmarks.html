Benchmarks

What we measured, and what we measure next.

Every number on this page comes with its hardware, its date, the version it was measured on, and a command to rerun it. Where we have not measured something yet, we say so instead of estimating.

How we benchmark

  • Rerunnable. The scripts live in the repository (benchmarks/), so you can run the same test on your own machine.
  • Hardware, date and version on every number. Laptop numbers are labelled as laptop numbers. Results below are for pyTracer 0.1.4.
  • The bad cases too. Abstentions, the request that failed, and the worst case next to the typical one.
  • Compared with running it live, not with other vendors. We do not publish numbers for tools we did not run ourselves.

Gateway ingestion: throughput, latency and loss

Will the gateway ever be my bottleneck, and does it lose spans?

One gateway, Redis queue and single-node ClickHouse from the bench stack, driven by k6 with batches of 20 spans, on an Apple M1 Pro laptop (Docker Desktop with 10 CPUs and 8 GB). Every count below is the gateway's own, not k6's.

RunResult
Ramp to 200 virtual users (2 min)The writer's ceiling on this laptop is about 3,600 spans/s. Past it the queue fills and the gateway answers 429 (backpressure, by design) instead of dropping spans; every accepted span was written, none dead-lettered.
Constant 150 and 180 requests/s (1 min each)p95 4.7 ms and 4.9 ms, no errors
Soak: 3,600 spans/s for 30 minutes324,001 requests and 6,480,020 spans; 0 failed, 0 rejected, 0 backpressured. p95 5.6 ms, median 3.0 ms, worst 329 ms. Accepted equals written (7,424,180 including earlier runs), 0 dead letters, and ClickHouse holds exactly that many distinct span ids. Gateway memory went from 99 MB to 75 MB.

One laptop, small spans (a few attributes each). Real model spans carry prompts and replies of several kilobytes, so expect lower throughput on real traffic; that is the next ingestion run below.

Measured · 26 Oct 2026

Two gateways, one of them killed mid-run

If a gateway crashes, do I lose the spans it was holding?

Two gateways sharing one Redis stream behind Caddy, at a constant 2,000 spans/s for 4 minutes. One gateway was stopped normally and restarted; the other was killed (SIGKILL) and restarted, mid-run.

  • No loss: 480,000 spans accepted, 480,000 distinct span ids stored, nothing left pending.
  • p95 stayed at 4.4 ms. The normal stop failed no request; the kill failed one, the request in flight on the killed gateway (the SDK retries it).
  • Delivery is at least once: the killed gateway had written part of a batch without acknowledging it, so its peer wrote that part again. Reads return each span once.
Measured · 26 Oct 2026

Self-hosting on a free-tier VM, with TLS

Can I run the whole stack myself, cheaply?

The full deploy stack (gateway, Redis, ClickHouse, Postgres and Caddy) ran on a Google Cloud free-tier e2-micro (1 GB of memory) with 2 GB of swap, using about 690 MB. Caddy obtained a Let's Encrypt certificate on the first try and the SDK delivered spans over HTTPS. A Redis restart under that setup is also how we found and fixed the bug that stopped the gateway writing after an outage (fixed in 0.1.4).

It fits, but tightly: for real use start at 2 to 4 GB. ClickHouse's own system logs grow without traffic (about 0.5 GB a week on our hosted server); capping them is on the roadmap.

Verdicts on real pull requests

Do the CI templates work, and is the verdict right?

We ran the shipped GitHub Action and /pytracer try on real pull requests in a test repository with a captured failure (an agent that undercounts its sources), installing pyTracer 0.1.4 from PyPI as the templates do, and the GitLab template on gitlab.com:

Pull requestExpectedThe posted verdict
The real fixfixedfixed
A README change, bug still therestill failingstill failing (0.1.3 wrongly said diverged)
Changes a tool call's argumentsno verdict, with the reasoncannot judge: "The branch calls tool 'search' with arguments the recording does not have", with the advice to re-record

Failing pushes opened one GitHub issue and later failures updated it instead of opening duplicates; the GitLab template ran in merge-request and branch pipelines with its JUnit report in the merge request.

Independent testing

An outside study of the verdicts

Does "fixed" mean fixed, on a real agent benchmark?

A partner tested 0.1.3 on a public agent benchmark with a planted bug and three candidate branches. Frozen replay was deterministic (20 of 20 identical replays, zero writes), but three verdict behaviours fell short of the docs, including a broken branch reported fixed because its calls had run live. All three are fixed in 0.1.4: a run that leaves its recording gets no verdict and the reason why, and a branch that fails exactly as before is reported still failing. We will link their report when it is public.

Run them yourself

From a clone of the repository, with Docker running:

docker compose -f benchmarks/docker-compose.bench.yml up -d --build
docker compose -f benchmarks/docker-compose.bench.yml --profile load run --rm k6
docker compose -f benchmarks/docker-compose.bench.yml --profile load run --rm \
  -e MODE=soak -e RATE=180 -e DURATION=30m k6
curl localhost:8080/v1/stats   # accepted must equal written, dead_letters 0

The benchmarks README explains every option and how to read the results.
